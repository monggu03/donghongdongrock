동아리에서 팀 프로젝트를 지켜보면 흔히 보는 장면입니다. 합치기는 자주 합니다. main에 바로 push하기도 하고, 기능마다 PR, 그러니까 main에 합쳐 달라는 요청을 올리기도 합니다. 그런데 자동 검사는 없고, 서버에는 한 번도 올려 보지 않습니다. (클릭) 그러다 발표 일주일 전, 처음으로 서버에 배포해 봅니다. 서버에서 빌드를 돌렸더니 실패합니다. 이상한 건, 이 코드가 제 컴퓨터에서는 잘 됐다는 점입니다. 이 에러의 정체는 뒤에서 밝혀집니다. (클릭) 겨우 고쳐서 띄웠더니 이번엔 데이터가 하나도 없습니다. 콘솔을 보면 API 주소가 아직 localhost입니다. 배포된 화면은 보는 사람의 브라우저에서 돌기 때문에, localhost는 그 사람 컴퓨터를 가리킵니다. 제 노트북에는 백엔드가 켜져 있어서 저만 잘 보였습니다. (클릭) 그다음은 환경 변수, CORS, DB 주소, 포트. 하나 고치면 다음 게 막히고, 발표 주간 내내 밤을 샙니다. (클릭) 실력 문제가 아닙니다. 합치기는 매일 했는데 검사와 배포는 마지막 주에 처음 해 본 구조가 문제입니다.

CI/CD는 방금 본 이 일을 사람 대신 기계가 하게 만드는 것입니다. 이 기계를 파이프라인이라고 부릅니다. 커밋을 실은 카트가 검사대를 하나씩 지나고, 포장과 보관, 스테이징을 거쳐 오른쪽 끝 운영 서버까지 갑니다. 매번 같은 순서입니다. (클릭) 앞쪽 절반이 CI, Continuous Integration, 지속적 통합입니다. 통합은 main에 합치는 것, 머지와 같은 말입니다. 합치기 전에 매번 자동으로 검사합니다. (클릭) 뒤쪽 절반이 CD입니다. 검사를 통과한 코드를 실제 서비스까지 보내는 부분입니다. 하나씩 따라가 보고, 마지막에 첫날 체크리스트를 드리겠습니다.

이제 CI가 있으면 어떻게 되는지 보겠습니다. 여기서부터 화면은 이 발표용으로 만든 시간표 예제 앱, 실습 레포에서 실제로 돌린 결과입니다. 시간표 기능을 고친 커밋을 올리고 PR을 엽니다. 카트에 붙은 글자가 커밋 번호입니다. (클릭) 그 순간 GitHub가 PR이 열린 걸 알고 검사를 자동으로 출발시킵니다. 아무도 버튼을 누르지 않았습니다. 달라진 건 PR마다 검사가 붙었다는 것 하나입니다.

검사대를 하나씩 통과: 설치 → 린트 → 테스트 → 빌드

앞 검사대를 통과해야 다음으로, 결과는 실습 레포의 실제 출력

테스트: 미리 적어 둔 기대값과 실제 결과 비교

빌드: 배포할 파일 만들기, 넷 다 통과하면 머지 가능

카트는 검사대를 하나씩 지나갑니다. 앞 검사대를 통과해야 다음으로 갑니다. (클릭) 먼저 설치. 잠금 파일에 적힌 버전 그대로 패키지를 설치합니다. (클릭) 린트. 안 쓰는 변수처럼 실수하기 쉬운 코드를 찾습니다. (클릭) 테스트. 미리 적어 둔 기대값과 실제 결과를 비교합니다. 여섯 개 다 통과. (클릭) 빌드. 실제로 배포할 파일을 만들어 봅니다. 넷 다 초록이면 PR에 초록 체크가 붙고, 머지 문이 열립니다.

이 검사들이 어디서 도는지 보겠습니다. 제 컴퓨터가 아닙니다. (클릭) GitHub가 빌려주는 깨끗한 리눅스 컴퓨터, 러너에서 돕니다. 이 파란 틀이 러너입니다. 실행이 끝나면 버려져서 매번 설치부터 다시 하고, 그래서 내 컴퓨터에만 깔린 무언가에 기대는 코드는 여기서 걸립니다. (클릭) 어떤 검사를 어떤 순서로 할지는 레포 안 yml 파일 하나에 적어 둡니다. GitHub Actions는 이 파일을 읽고 러너에서 실행해 주는 서비스입니다.

PR 트리거는 보통 파일 밖 설정

  

  
회사에 가면 GitHub Actions 대신 Jenkins나 GitLab CI를 쓰는 곳이 많습니다. GitHub Actions는 GitHub에 들어 있는 자동화입니다. 도구는 달라도 트리거, 러너, 단계 세 자리는 같습니다. 여기서는 on, runs-on, steps입니다.
(클릭) Jenkins는 회사가 직접 서버에 설치해서 운영하는 자동화 서버입니다. 러너는 agent, 단계는 stages로 바뀌고, PR이 열릴 때 출발시키는 트리거는 보통 파일 밖 Jenkins 설정에 둡니다.
(클릭) GitLab CI는 GitLab에 들어 있습니다. 트리거는 rules, 러너는 image, 단계는 script입니다. 문법만 다르고 세 자리는 같습니다.

칸별로 보면 이렇습니다. 칸은 그대로이고 이름만 바뀝니다. 사내나 금융권에서는 Jenkins, Nexus, 사내 쿠버네티스를 많이 씁니다. 면접에서 물어보시면 그 회사 개발 문화가 보입니다.







  
학생 프로젝트에서 잘 안 돌아가는 이유

  

    
흔한 생각바꾸면

    
      
배포는 발표 직전에 하는 것첫날 Hello World 배포

      
테스트가 없으니 CI는 필요 없음린트와 빌드만 걸어도 사고 차단

      
main에 바로 push해도 됨브랜치 보호로 검사 통과한 PR만

    
  

  
이제 여러분 프로젝트로 가져가 보겠습니다. 학생 프로젝트에서 CI/CD가 잘 안 돌아가는 이유는 대개 세 가지입니다. 첫째, 배포를 발표 직전에 한 번 하는 행사로 생각하는 것. 첫날 Hello World를 배포해 두면 발표 주간의 배포는 그냥 또 한 번의 배포입니다.
(클릭) 테스트가 없으니 CI가 필요 없다고 생각하는 것. 린트와 빌드만 걸어도 오늘 본 사고 두 개는 막힙니다.
(클릭) 그리고 main에 바로 push하는 것. 아까 본 브랜치 보호 한 번이면 검사를 통과한 PR만 main에 들어갑니다.






  
첫날 한 시간 체크리스트

  
    
    
  • 두 레포에 ci.yml 복사명령만 프로젝트에 맞게
    • 
    
  • 프론트는 Vercel 연결레포 Import 한 번
    • 
    
  • 백엔드는 Hello World를 Cloud Run에 첫 배포키 파일 없는 배포 권한 연결(WIF)은 gcp-setup.sh 한 번
    • 
    
  • 두 레포 main 보호: PR 필수 + 필수 검사 + 우회 금지GitHub 무료 요금제는 공개 레포만 보호 가능, 해커톤 레포는 공개가 간편
    • 
  

  
그래서 프로젝트 첫날 한 시간 안에 이것만 해 두시길 권합니다.
(클릭) ci.yml 복사. 파일은 가이드북에 그대로 들어 있고, 발표 일주일 전에 터진 빌드 실패가 첫 PR부터 잡힙니다.
(클릭) Vercel 연결. 배포 주소를 폰으로 한 번 열어 보면 localhost 문제가 첫날 걸립니다.
(클릭) 백엔드 Hello World를 Cloud Run에 첫 배포. 비밀 키 없이 GitHub가 구글 클라우드에 배포하게 이어 주는 WIF도 가이드북 스크립트 한 번이면 됩니다.
(클릭) 그리고 브랜치 보호. PR 필수, 필수 검사, 우회 금지를 켭니다. 필수 검사는 PR로 한 번 돌려 본 뒤에야 목록에 뜹니다. GitHub 무료 요금제에서는 공개 레포만 보호 규칙이 걸리니, 해커톤 레포는 공개로 만드시는 게 편합니다.
