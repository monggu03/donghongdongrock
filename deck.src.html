문제가 한꺼번에 터지면 어디서 깨졌는지 찾기 어려움

이건 실력 문제가 아닙니다. 2주 동안 한 번도 합치지 않았고, 한 번도 서버에 올려 보지 않은 구조가 문제입니다. 문제가 한꺼번에 터지면 어디서 깨졌는지 찾기가 어렵습니다.

CI작게, 자주 합치기 CI합칠 때마다 기계가 검사 CD통과하면 바로 배포

문제가 생겨도 어제 이후 바뀐 한 줄만 보면 됨

CI/CD는 이 순서를 뒤집습니다. 작게, 자주 합치고. 합칠 때마다 사람 대신 기계가 검사하고. 통과하면 바로 배포합니다. 그러면 문제가 터져도 어제 이후 바뀐 한 줄만 보면 됩니다.

CI: 합칠 때마다 자동 검사

Continuous Integration · 지속적 통합

내 변경PR
자동 검사lint · test · build
main에 합침

하나라도 실패하면 합치지 않음

먼저 CI입니다. Continuous Integration, 지속적 통합. 내 변경을 main에 합치기 전에 기계가 자동으로 검사합니다. 하나라도 실패하면 합치지 않고 돌려보냅니다.

CD: 검사를 통과하면 배포까지

Continuous Delivery / Continuous Deployment

검사 통과
배포빌드 결과를 서버에 올림
실제 서비스

CD의 D는 두 가지, 차이는 다음 장에서

CD는 검사를 통과한 코드를 실제 서비스까지 보내는 겁니다. 그런데 CD의 D가 두 가지입니다. Delivery와 Deployment. 차이는 딱 하나입니다.

일부러 깨뜨려 보기

실습 레포 cicd-frontend에서 PR 하나로 실패부터 통과까지

이제 직접 깨뜨려 보겠습니다. 실습용 프론트 레포에서 PR 하나를 열어서, 실패하고, 막히고, 고쳐서 통과하는 것까지 한 번에 보여 드리겠습니다.

실습 대상: 845분을 "14:05"로 바꾸는 함수

export function toHHMM(totalMinutes) {
  const h = Math.floor(totalMinutes / 60) % 24
  const m = totalMinutes % 60
  return `${String(h).padStart(2, '0')}:${String(m).padStart(2, '0')}`
}
expect(toHHMM(845)).toBe('14:05')

입력

845

결과

14:05

실습 대상은 세미나 시간표를 만드는 작은 함수입니다. 845분을 받으면 "14:05"로 바꿔 줍니다. 그리고 845를 넣으면 "14:05"가 나와야 한다는 테스트가 하나 있습니다.

"굳이 필요한가" 싶어 padStart를 지운 한 줄

 const m = totalMinutes % 60
-return `${String(h).padStart(2, '0')}:${String(m).padStart(2, '0')}`
+return `${h}:${m}`
 }
Lint 통과 Build 통과 화면도 뜸, 시간만 14:0 – 14:10

Vercel만 있었다면 이대로 운영에 배포

누군가 padStart가 굳이 필요한가 싶어서 이렇게 지웠다고 해 보겠습니다. lint도 통과하고 빌드도 됩니다. 화면도 뜹니다. 시간만 14:0처럼 이상하게 나옵니다. Vercel만 있었다면 이 코드가 그대로 운영에 나갑니다.

Jenkins 트리거는 파일 밖 웹훅 설정

회사에 가면 GitHub Actions 대신 Jenkins나 GitLab CI를 쓰는 곳이 많습니다. 그런데 탭을 바꿔 보면 문법만 다르고 트리거, 러너, 단계는 같은 자리에 있습니다. Jenkins는 트리거를 파일 밖 웹훅으로 설정합니다.

회사에서는 칸마다 도구 이름만 바뀜

칸이 실습AWS사내·금융권
CI 실행기GitHub ActionsCodeBuildJenkins
결과물 보관Artifact RegistryECRNexus
실행 환경Cloud RunECS, EC2사내 쿠버네티스
배포 인증WIFIAM 역할 + OIDC사내 계정, 결재
칸별로 보면 이렇습니다. AWS로 하면 결과물은 ECR에, 실행은 ECS나 EC2에. 사내나 금융권에서는 Jenkins, Nexus, 사내 쿠버네티스를 많이 씁니다. 특히 금융권은 배포 전에 승인 절차를 거치는 Delivery 형태가 흔합니다. 회사와 시기마다 다르니 면접에서 물어보시면 그 회사 개발 문화를 알 수 있습니다.

학생 프로젝트에서 잘 안 돌아가는 이유

흔한 생각바꾸면
배포는 마지막 날 하는 것첫날 Hello World 배포
테스트가 없으니 CI는 필요 없음lint와 build만 걸어도 사고 차단
팀 규칙은 말로 정하면 됨브랜치 보호로 시스템이 지킴
학생 프로젝트에서 CI/CD가 잘 안 돌아가는 이유는 대개 이 세 가지입니다. 배포를 마지막 날 하는 이벤트로 생각하는 것. 첫날 Hello World를 배포해 두면 마지막 날은 그냥 또 한 번의 배포입니다. 테스트가 없으니 CI가 필요 없다고 생각하는 것. lint와 build만 걸어도 오늘 본 사고 두 개는 막힙니다. 그리고 팀 규칙을 말로만 정하는 것.

첫날 한 시간 체크리스트

  • 두 레포에 ci.yml 복사명령만 프로젝트에 맞게
  • 프론트는 Vercel 연결레포 Import 한 번
  • 백엔드는 WIF 연결 후 Hello World를 Cloud Run에 첫 배포실습 레포의 gcp-setup.sh
  • 두 레포 main 브랜치 보호 + 필수 검사 지정팀이면 승인 1명
그래서 프로젝트 첫날 한 시간 안에 이것만 해 두시길 권합니다. ci.yml 복사, Vercel 연결, 백엔드 Hello World를 Cloud Run에 첫 배포, 그리고 브랜치 보호. 이후로는 PR 하나가 검사 한 번, 배포 한 번이 됩니다.
